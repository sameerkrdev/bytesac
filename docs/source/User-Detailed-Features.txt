## Detailed Features

## 1. Overview

- Users can connect wallets across supported blockchains.
- Users own their underlying assets.
- Users can invest in manager-created baskets.
- Managers define basket strategies and target allocations.
- The platform executes asset acquisition/rebalancing according to the basket strategy.
- Users retain control over whether to participate in rebalances.
- Users can withdraw/cancel their investment at any time.
- Portfolio state and transactions are verifiable on-chain.
- Manager and organization information is separately verified by the platform.

---

# 2. Public Basket Discovery

Users **do not need to log in** to explore the platform.

Unauthenticated users can:

- View available baskets
- View basket performance
- View basket strategy
- View asset allocation
- View asset weightages
- View manager information
- View organization/firm information
- View manager experience
- View basket fees
- View rebalance frequency
- View minimum investment amount
- View supported assets
- View sector allocation
- View historical changes
- Research the basket before investing

The purpose is to make basket discovery completely public while requiring authentication only when the user wants to perform an investment action.

# 6. User Authentication

Users can browse baskets without authentication.

Authentication becomes necessary when the user wants to invest or perform account-specific actions.

The authentication flow is wallet-based:

```
Connect Wallet
      ↓
Wallet signature
      ↓
Backend verifies signature
      ↓
Identify User
      ↓
Identify Investment Wallet
      ↓
Create / refresh session
      ↓
Authenticated User
```

The existing architecture uses Reown / WalletConnect for wallet connection, backend signature verification, and Supabase for the application session layer.

---

# 7. Multi-Chain Wallet Support

Users can use supported wallets across supported chains.

```
       ├── BNB
```

with users eventually being able to add wallets from settings.

# 11. Investment Example

Suppose a basket has:

```
BTC       25%
SOL       30%
ETH       10%
RWA       35%
```

The user invests:

```
100 USDC
```

The target allocation is:

```
BTC       25 USDC
SOL       30 USDC
ETH       10 USDC
RWA       35 USDC
```

However, the user should **not expect exactly 100 USDC worth of acquired assets** because execution costs may apply.

Potential costs include:

- Platform fee
- Basket/manager fee
- DEX fee
- RWA execution fee
- Slippage
- Network/transaction fee
- Other applicable execution costs

Therefore:

```
100 USDC
   ↓
Investment amount
   ↓
Fees + execution costs
   ↓
Net capital deployed
   ↓
Asset acquisition
```

> 

Conceptually:

```

 ↓

 ↓
```

# 15. No Lock-in

Users should not have a mandatory investment lock-in period.

The intended behavior is:

```
Invest
  ↓
Hold
  ↓
Withdraw whenever user wants
```

The user can choose to leave the basket without waiting for a scheduled maturity period.

# 17. Cancel Basket

Users should also be able to stop following a basket.

```
Basket
  ↓
Cancel / Exit
  ↓
User stops participating
```

The platform should distinguish:

```
Cancel following basket
```

from:

```
Withdraw assets
```

because these are conceptually different operations.

For example:

```
Cancel basket
→ Stop future rebalance participation

Withdraw
→ Convert/transfer the user's holdings
```

The exact UX can combine them when the user wants to fully exit.

# 20. Basket Updates

A manager can publish a new basket version.

The existing basket architecture treats the manager's strategy as a **versioned model portfolio** rather than overwriting the previous allocation.

Example:

### v1

```
BTC 25%
SOL 30%
ETH 10%
RWA 35%
```

Manager publishes:

### v2

```
BTC 30%
SOL 25%
ETH 15%
RWA 30%
```

The user's existing portfolio is not silently changed.

---

# 21. Rebalance Notification

When a new basket version is published:

```

User reviews rebalance
```

> 
>

>

>

>

# 22. User Controls Rebalance Participation

The user has two choices:

```
[Participate]
[Skip]
```

The manager publishing a new version **does not automatically execute a trade in the user's portfolio**.

This preserves user control.

The existing architecture explicitly defines the behavior that a user can review, apply, or skip a manager rebalance.

# 26. Skipping a Rebalance

If the user chooses:

```

```

```

```


---

# 27. Multiple Skipped Rebalances

If the user skips:

```
v2
v3
v4
```

and later chooses to participate in:

```
v5
```

the platform should **not replay**:

```
v1 → v2
v2 → v3
v3 → v4
v4 → v5
```

Instead:

```
CURRENT ACTUAL PORTFOLIO
           ↓
LATEST TARGET v5
           ↓
ONE EXECUTION PLAN
```

This is explicitly part of the current portfolio/rebalance architecture.

# 28. Portfolio Drift

Users can manually modify their portfolio.

For example, the basket target is:

```
BTC 40%
ETH 30%
SOL 30%
```

The user independently sells SOL.

Now the portfolio may become:

```
BTC 40%
ETH 30%
SOL 0%
USDC 30%
```

This creates:

```
PORTFOLIO DRIFT
```

The platform should detect this rather than assuming the user's holdings always equal the manager's model.

---

# 29. Drift Detection

The platform continuously/recurrently reconciles:

```
Manager Target
      vs
User Actual Holdings
```

Conceptually:

```
Target
  │
  │ compare
  ▼
Actual
  │
  ├── Aligned
  │
  └── Drifted
```

The existing architecture defines the blockchain as the source of truth for actual portfolio state, with the portfolio reconciler comparing expected and actual holdings.

---

# 30. Drift Notification

If significant drift is detected:

> **Portfolio drift detected**
> 
> 
> Your current portfolio no longer matches the basket's target allocation.
> 
> SOL: 30% target → 0% actual
> 
> USDC: 0% target → 30% actual
> 
> [Review Portfolio]
> 

No automatic buyback should occur merely because the user manually changed their holdings.

---

---

# 32. Customized Portfolio

The user may intentionally want to deviate from the manager.

Therefore, the platform should support:

```
Keep Custom Allocation
```

Example:

```
Manager Target:

BTC 40%
ETH 30%
SOL 30%

User:

BTC 45%
ETH 40%
SOL 15%
```

The user can explicitly maintain this customized state.

The platform should not repeatedly attempt to restore the manager's allocation without user authorization. The existing architecture distinguishes **ALIGNED**, **DRIFTED**, and **CUSTOMIZED** states for this reason.

---

# 33. Portfolio States

Recommended user-facing states:

### ALIGNED

```
Actual ≈ Target
```

No action required.

### REBALANCE AVAILABLE

```
New manager version available
```

User needs to review.

### DRIFTED

```
Actual ≠ Target
```

User can review/fix.

### CUSTOMIZED

```
User intentionally deviates from strategy
```

### EXECUTION PENDING

```
Transaction awaiting execution/confirmation
```

### EXECUTION FAILED

```
Execution did not fully complete
```

```
                     ▼

                     │
```

Every execution should have constraints such as:

```
Maximum slippage
Minimum output
Transaction deadline
Allowed assets
Allowed execution venues
Basket version
Portfolio ID
```

A stale execution plan should expire rather than executing against materially changed market conditions.

```
SUCCESS
PARTIAL
FAILED
```
