## Fund Manager & Organisation Onboarding Flow

## 1. Purpose

This document defines the proposed fund-manager onboarding and organization lifecycle for the platform.

The key design principle is:

> **A fund manager is onboarded through an Organization, while the person authenticates through a User account and wallet.**
> 

The platform separates:

- User authentication
- Fund-manager application
- Organization creation
- Organization verification
- Organization membership
- Organization payout wallet
- Basket ownership/management
- Public manager history
- Platform verification

This allows an individual manager and a professional firm to use the same core organization model while keeping private verification information separate from public information.

# 3. Core Entities

The system should keep these concepts separate.

```
User
  │
  ├── Authentication wallet
  ├── Email
  ├── Phone
  └── Investor account
       │
       └── Investment wallet

User
  │
  └── Organization Membership
           │
           ▼
      Organization
           │
           ├── Owner
           ├── Members
           ├── Payout Wallet
           ├── Verification
           ├── Public Profile
           └── Baskets
```

Important:

```
USER ≠ ORGANIZATION ≠ WALLET ≠ MEMBERSHIP
```

A person can:

- be a normal investor;
- own an organization;
- belong to other organizations;
- manage baskets;
- invest in baskets;
- perform different roles in different organizations.

# 4. Stage 1 — Become a Fund Manager Application

The public platform contains:

```
Become a Fund Manager
```

The applicant submits an initial application.

The first form should collect enough information for your team to understand and screen the applicant, but it should not necessarily contain the complete KYC/KYB package.

## Initial Application

### Applicant

```
Applicant type
- Individual
- Firm / Company

Full name
Email
Phone
Country / jurisdiction
Website
Professional background
Investment experience
Relevant qualifications
Reason for becoming a manager
Types of baskets they intend to create
```

The applicant also provides:

```
Wallet address
```

However:

> **Do not treat a typed wallet address as proof of ownership.**
> 

The address is only an identifier until ownership is cryptographically verified.

---

# 5. Stage 2 — Platform Team Contact

After application submission:

```
Application
    ↓
Submitted
    ↓
Internal Screening
    ↓
Team Contacts Applicant
```

Your team can communicate with the applicant and perform the initial screening.

Possible statuses:

```
SUBMITTED
SCREENING
CONTACTED
ADDITIONAL_INFORMATION_REQUIRED
SCREENING_APPROVED
SCREENING_REJECTED
```

This stage is intentionally lightweight.

The purpose is to decide whether the applicant should proceed to the full organization setup.

---

# 6. Stage 3 — Basic Verification

Your team performs the initial/basic verification.

This can include:

```
Identity sanity check
Contact verification
Professional background check
Basic experience review
Basic wallet review
Conflict / risk screening
```

The exact checks should depend on the jurisdictions and asset types supported by the platform.

If the applicant passes:

```
screening_status = approved
```

The platform can proceed to wallet authentication and organization creation.

---

# 7. Stage 4 — Wallet Address Verification

The applicant provides a wallet address.

The platform determines whether that wallet already belongs to a User.

```
Wallet Address
      │
      ▼
Search wallet
      │
 ┌────┴─────┐
 │          │
Exists    Doesn't exist
 │          │
 ▼          ▼
Use       Create
existing  pending User
User          │
              ▼
        Verify wallet ownership
```

## Important change from the original proposal

Do **not** create an immediately active account merely because someone typed an address.

Recommended process:

```
Wallet address submitted
        ↓
Pending user created if needed
        ↓
User connects wallet
        ↓
User signs authentication message
        ↓
Wallet ownership verified
        ↓
User account activated
```

This prevents someone from claiming another person's wallet address.

# 8. Existing User

If the wallet already belongs to an existing platform user:

```
Application
    ↓
Wallet matched
    ↓
Existing User identified
    ↓
Grant organization-creation permission
```

The user retains their existing investor account.

The platform does not convert the user into a different account.

Instead:

```
Existing User
    │
    ├── Investor
    │
    └── Organization Owner
```

# 9. New User

If the wallet does not belong to an existing platform user:

```
Application
    ↓
Wallet address received
    ↓
No matching User
    ↓
Create pending User record
    ↓
User connects wallet
    ↓
User signs message
    ↓
Wallet ownership verified
    ↓
User account activated
    ↓
Grant organization-creation permission
```

The newly created user can then log into the platform.

# 10. Organization Creation Permission

Passing the initial fund-manager screening should grant a special platform permission.

Example:

```
can_create_manager_organization = true
```

This is better than immediately giving the user a permanent manager role.

The permission means:

> "This user has passed the initial screening and is allowed to create a manager organization application."
> 

It does **not** mean:

> "This organization has already been verified."
>

# 14. Organization Payout Wallet

During organization setup, the Owner must provide a dedicated Solana wallet.

Purpose:

> **Receive basket fees / manager-related payouts.**
> 

This wallet should be modeled separately from:

- the owner's personal/investor wallet;
- the owner's authentication wallet;
- other organization wallets;
- execution wallets.

Recommended model:

```
Organization
    │
    └── Payout Wallet
           │
           ├── chain = Solana
           ├── address
           ├── ownership_verified
           └── status
```

---

# 15. Payout Wallet Ownership Verification

The Owner provides:

```
Solana wallet address
```

Then:

```
Enter wallet
      ↓
Connect wallet
      ↓
Sign verification message
      ↓
Verify ownership
      ↓
Save payout wallet
```

The platform should never assume that entering an address proves control of the wallet.

Recommended status:

```
UNVERIFIED
VERIFYING
VERIFIED
REPLACEMENT_PENDING
REVOKED
```

---

# 16. Changing the Organization Payout Wallet

The Owner can request a replacement.

Example:

```
Current payout wallet
Solana: ABC...XYZ

[Change Wallet]
```

Recommended flow:

```
Owner requests wallet change
        ↓
New Solana wallet submitted
        ↓
New wallet ownership signature
        ↓
Platform verification / security checks
        ↓
New wallet approved
        ↓
Old wallet becomes inactive
        ↓
New wallet becomes active
```

Do not simply overwrite the old address.

Keep the history:

```
Wallet A
  active: 2026-01-01 → 2026-09-27

Wallet B
  active: 2026-09-27 → present
```

This creates an auditable history.

For security-sensitive wallet changes, consider requiring an additional platform review or delay before the replacement becomes active.

# 18. Organization Verification

The platform team reviews:

```
Organization information
Documents
Identity
Business information
Ownership
Experience
Wallet ownership
Required compliance checks
```

The result can be:

```
APPROVED
```

or:

```
REJECTED
```

or:

```
CHANGES_REQUIRED
```

The `CHANGES_REQUIRED` state is important because it allows your team to ask for missing or incorrect information without forcing the applicant to restart the process.

---

# 19. Recommended Organization Statuses

Use a proper state machine.

```
DRAFT
   ↓
SUBMITTED
   ↓
UNDER_REVIEW
   │
   ├── CHANGES_REQUIRED
   │        │
   │        ▼
   │     RESUBMITTED
   │        │
   │        └──────► UNDER_REVIEW
   │
   ├── REJECTED
   │
   └── APPROVED
          ↓
       VERIFIED
```

Do not use only:

```
approved = true/false
```

The state history is important for auditability.

# 22. Organization Changes After Verification

This is one of the most important parts of the new design.

Once an organization is verified, the Owner must not directly overwrite verified public information.

Instead:

```
Verified Organization
       ↓
Owner edits information
       ↓
Create Change Request
       ↓
Pending Verification
       ↓
Platform Review
       ↓
Approved
       ↓
New information becomes public
```

Until approval:

> **The currently approved public information remains visible.**
> 

The pending changes should not replace the verified public version.

```

# 30. Member Removal

The new flow is correct in one important respect:

> **Removing a member should remove the organization membership, not erase the historical person or basket records.**
> 

Recommended flow:

```
Owner
  ↓
Remove / Revoke Member
  ↓
Membership status = REVOKED
  ↓
Member loses organization permissions
  ↓
Historical relationship preserved
```

Do not hard-delete the membership.

---

# 31. What Happens to the Member's Baskets?

This requires an important refinement to the proposed flow.

Do not automatically delete a basket because its manager leaves.

Instead separate:

```
Basket
```

from:

```
Basket Manager Assignment
```

Example:

```
Basket
  ├── Basket ID
  ├── Versions
  ├── Performance history
  ├── Investors
  └── Current Manager
```

and:

```
Manager Assignment
  ├── Basket
  ├── Organization
  ├── User
  ├── Role
  ├── Started At
  └── Ended At
```

This allows the historical record to survive.

---

# 32. Manager Removal From a Basket

Suppose:

```
ABC Capital
   │
   └── Alice manages
          │
          └── Crypto Index
```

Alice leaves.

Do not erase:

```
Crypto Index
```

Instead:

```
Alice
  │
  └── Manager Assignment
          status = ENDED
          ended_at = ...
```

The basket can then enter a defined state such as:

```
MANAGER_REMOVED
```

or:

```
MANAGER_REVIEW_REQUIRED
```

depending on your product policy.

# 33. Critical Product Decision: Basket Ownership vs Manager Attribution

You need to explicitly define:

> Does a basket belong to the Organization, or to the individual Manager?
> 

For the architecture we have been building, the cleanest model is:

```
Basket belongs to Organization
```

while:

```
Manager is assigned to the Basket
```

Therefore:

```
Organization
    │
    └── Basket
           │
           └── Manager Assignment
                  │
                  └── User
```

This means when a manager leaves:

- the organization keeps the basket;
- the manager's historical association remains;
- the manager loses edit permissions;
- the basket can be paused, reassigned, or retired according to policy;
- investors can see the manager history.

This is substantially safer than deleting or transferring ownership implicitly.

# 38. Basket State When Manager Leaves

You need an explicit policy.

Recommended states:

```
DRAFT
UNDER_REVIEW
PUBLISHED
PAUSED
MANAGER_REMOVED
REASSIGNMENT_REQUIRED
RETIRED
ARCHIVED
```

Example:

```
Manager removed
      ↓
Basket = REASSIGNMENT_REQUIRED
      ↓
Organization assigns new manager
      ↓
Platform verifies required changes
      ↓
Basket returns to PUBLISHED
```

Alternatively, if your policy allows the basket to remain active under the organization without a named individual manager, you can define:

```
Current Manager = Organization
```

But this should be an explicit business rule rather than an accidental side effect.

  ↓
Update public manager history
  ↓
Notify affected investors
```

# 43. Important Changes From the Previous Architecture

## Change 1 — Manager application and organization creation are separate

### Previous

```
Application
   ↓
Verification
   ↓
Manager Account
   ↓
Manager Workspace
```

### New

```
Application
   ↓
Initial Screening
   ↓
Wallet Authentication
   ↓
User
   ↓
Organization Creation
   ↓
Organization Verification
   ↓
Manager Workspace
```

This is a cleaner separation between the person and the organization.

---

# 44. Change 2 — Manager is no longer a simple User role

Previously the conceptual model included:

```
User
 └── Role
      ├── Investor
      └── Fund Manager
```

The new architecture should instead emphasize:

```
User
 ├── Investor
 │
 └── Organization Membership
        └── Organization
              └── Manager permissions
```

The user is a person.

The organization is the manager entity.

The membership grants the person authority within that organization.

---

# 45. Change 3 — Organization becomes the durable owner of baskets

Recommended:

```
Organization
   │
   └── Basket
          │
          └── Manager Assignment
```

Not:

```
Individual User
   │
   └── Basket
```

This is especially important for firms.

If an employee leaves:

```
Employee leaves
     ↓
Membership revoked
     ↓
Basket remains with organization
```

---

# 46. Change 4 — Payout wallet is a dedicated organization resource

Do not mix:

```
User authentication wallet
```

with:

```
Organization payout wallet
```

Recommended:

```
User Wallet
     ↓
Authentication / personal investing

Organization Payout Wallet
     ↓
Basket fees / organization payouts
```

The payout wallet is verified separately.

---

# 47. Change 5 — Organization changes require re-verification

The new requirement is stronger than the previous model.

Do not let:

```
Verified Organization
```

be directly edited into:

```
New Public Organization
```

Instead:

```
Verified Version
      ↓
Change Request
      ↓
Review
      ↓
Approved Version
```

This protects the integrity of public manager information.

---

# 48. Change 6 — Membership has its own verification workflow

A member should not become active merely because the Owner adds their wallet.

Instead:

```
Owner proposes member
      ↓
Platform verification
      ↓
Wallet ownership proof
      ↓
Documents
      ↓
Approval
      ↓
Membership active
```

---

# 49. Change 7 — Historical records must never be deleted

For:

```
Organizations
Members
Manager assignments
Baskets
Basket versions
Wallets
Verification decisions
Public profiles
```

prefer:

```
status + timestamps + history
```

over hard deletion.

This is particularly important for investment products where users may need to understand historical manager relationships.

---

# 50. Change 8 — Public history becomes a first-class concept

The platform should not only show:

```
Current Manager
```

It should also maintain:

```
Manager History
```

This allows investors to understand:

```
Who managed this basket?
When?
Who manages it now?
When did the change happen?
```

# 52. Final Product Principles

### Principle 1

> **Wallet proves control of an identity, not organization approval.**
> 

### Principle 2

> **User identity and organization identity are separate.**
> 

### Principle 3

> **Organization owns the manager business context and baskets.**
> 

### Principle 4

> **Membership grants a user authority inside an organization.**
> 

### Principle 5

> **Sensitive verification information stays private.**
> 

### Principle 6

> **Public verified information changes only after platform approval.**
> 

### Principle 7

> **Payout wallet is separate from personal/authentication wallets.**
> 

### Principle 8

> **Removing a member removes permissions, not history.**
> 

### Principle 9

> **Removing a manager does not automatically delete the basket.**
> 

### Principle 10

> **Manager changes affecting investors generate appropriate notifications.**
> 

### Principle 11

> **All important verification and membership changes are auditable.**
> 

### Principle 12

> **The organization remains the durable entity even when individual managers change.**
>
