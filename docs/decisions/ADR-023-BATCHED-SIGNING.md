# ADR-023: Batched signing groups and user-paid Solana gas

- **Status:** APPROVED; P1 and P1b IMPLEMENTED (first investment on Solana, website; faster fee landing and MetaMask sign-and-send)
- **Date:** 2026-10-11
- **Owners:** Product owner (user), engineering
- **Related:** D-067, D-068, D-072, D-073, D-090, D-094, D-123 to D-130; ADR-014, ADR-015, ADR-016, ADR-017; `docs/superpowers/specs/2026-10-11-batched-signing-direct-routes-design.md` (B-01 to B-27); `docs/superpowers/plans/2026-10-11-spec22-p1-first-investment.md`, `docs/superpowers/plans/2026-10-11-spec22-p1b-landing-and-metamask.md`

## Context
ADR-014 made the user sign one leg at a time and made the platform pay Solana gas as co-signing fee payer. A 12-asset basket meant 13 wallet popups, each with a fresh 60 s quote. The platform fee payer needed funding, per-user and global caps, reservations and a sponsorability retry loop, and wallets that rewrite a transaction (Phantom priority-fee padding, a replaced fee payer) kept failing with `TX_MISMATCH`. A failed leg ended the operation `PARTIAL` or `FAILED` and the user had to start over.

## Decision
P1 covers the first investment on the website. Sells, repairs and rebalances keep the per-leg flow (P2, P3).

- **Signing groups (B-01).** The legs of one operation that share a source chain are signed in groups: quoted together and approved in one wallet interaction. A group is formed at request time from the first `PLANNED` Solana legs in sequence order (`operation_groups`, one open group per operation and chain).
- **Solana sign-only batch (B-02).** The wallet signs the whole chunk with `signAllTransactions`. The server verifies every transaction (message identical to the quote or differing only in ComputeBudget, the user as fee payer, a valid ed25519 signature) before it claims any, claims them all in one transaction (claim before send, D-071), sends the fee transfer with preflight and waits for `confirmed`, then sends the asset legs in order and stops at the first definitive refusal. A refused fee releases every claim (503 `ROUTE_UNAVAILABLE`). The send loop runs in the request, never in a job (D-018).
- **Chunk size (B-17).** `K_SIGN_ALL = 12` and `K_SIGN_AND_SEND = 12` in `@repo/validator`; a group holds at most K transactions (K − 1 asset legs plus the fee when a fee is charged), so 12 assets and the fee are 13 transactions and two approvals. Tuned from the P0 wallet lab and production telemetry (OPEN-ITEMS). Tier `single` (a wallet that signs one transaction per popup) cannot sign 12 in the 40 s window, so its groups are small: while uncovered fee shares exist the first group holds only the fee transfer, charging the uncovered shares of every `PLANNED` Solana leg; after that each group holds one asset leg (approvals = legs + 1).
- **`sendBy` and the blockhash gate.** `sendBy = quotedAt + 40 s` (`GROUP_SEND_WINDOW_MS`). A submit after `sendBy` is 409 `GROUP_EXPIRED` with nothing claimed (the group is `EXPIRED` and its `PLANNED` legs leave it, so the next group request can take them again), and the fee wait is capped at `min(30 s, sendBy − now)`. Each asset leg is gated by its real blockhash: it is sent only if `isBlockhashValid(recentBlockhash, "confirmed")` holds and the block height is at most `quoteBlockHeight + 150 − 20`. The first leg that fails, and every later one, is released unsent with `lastError: "QUOTE_STALE"`. The block height is read before the quotes, so a quote's blockhash is never older than `quoteBlockHeight`.
- **The user pays Solana gas in SOL (B-03, B-23).** Every Solana-source leg is `gasPayer: "user_solana"`, on the group and the per-leg endpoints (mobile too). LI.FI quotes carry no `svmSponsor` and the user is the fee payer. The user also pays the rent of the token accounts a transaction creates, counted only for accounts that do not exist yet (`CreateIdempotent` is in every LI.FI and fee transaction; the accounts are read with `getMultipleAccountsInfo`, and one behind a lookup table or an RPC error counts as missing). The SOL requirement is `Σ (5 000 × signatures + priority fee) + rent of missing accounts + native SOL sold + SOL_BUFFER_LAMPORTS (1 000 000)`; a shortfall is 409 `SOL_REQUIRED` with `details { lamportsRequired, lamportsHeld }`, checked at plan time and again at group quote. There is no SOL top-up (D-094). A plan with nothing charged has no fee leg.
- **No LI.FI integrator fee (B-05).** The fee stays our own server-built transfer (D-089), so a LI.FI transaction is never edited.
- **Fee per group (B-06).** Each asset leg gets a fee share per kind at plan time (`floor(total × legBase / Σ legBase)`, remainder to the largest base). A group's fee transfer charges the uncovered shares of its own legs, in the order network, manager, platform; a kind summing to 0 is left out. The plan's fee leg is reused by the first group (its amount changes only while `PLANNED` and unclaimed); a later group adds a fee leg only while shares remain uncovered. A group never sent is never charged; a fee that was sent is not refunded.
- **`operation_fee_charges`.** A charge is written per settled fee leg and per kind (from `routeSummary.feeCharges`), with the block time. `operation_legs.fee_covered_by` names the fee leg that charged a leg's share. Earnings, revenue and reconciliation read charges; existing `operation_fees` rows were backfilled into charges. A fee leg that never settles writes nothing.
- **Failures stay open (B-08, B-09).** A grouped invest with a failed or unsent leg stays `IN_PROGRESS` with `needsAction`. The user can Continue (new quotes for the remaining legs, balances rechecked, old bytes never reused), Raise slippage (up to 3%), Skip an asset, Invest what's available (remaining amounts and uncovered shares scaled by available ÷ needed) or Stop (`PARTIAL` if an asset leg settled, else `FAILED`). A Continue that names no slippage keeps the operation's own, and a replay of one answers the same view even if it ended the investment. Continue is refused while a leg is in flight and never resends an unknown one. The 5-minute sweep stops an invest after 24 h without progress (`INVEST_AUTO_STOP_HOURS`; rebalance and sell will use 7 days when they get groups), audit `operation.auto_stopped`, notice `execution_incomplete`. Progress is the later of the last needs-action mark and the last group quoted, because quoting clears the mark and a wallet popup that is closed never reaches the server; an investment with a recovery that is not final is skipped (the recovery keeps its own 7-day stop, D-096). Skipping every remaining leg also ends it.
- **Website only (B-21).** The website uses the group endpoints (`POST /v1/operations/:id/groups`, `.../groups/:groupId/submit`, `POST /v1/operations/:id/continue`; Stop is the existing cancel). Mobile keeps the per-leg endpoints; its Solana legs become user-paid in P1. The device check of mobile invest with user-paid SOL is in OPEN-ITEMS.

### Faster landing and MetaMask sign-and-send (P1b, B-24 to B-27)
The first live run with MetaMask showed a fee transaction that took minutes to confirm (every buy was then released as `QUOTE_STALE`) and one MetaMask popup per transaction. Causes: the fee requested 1 400 000 compute units at a fixed 16 001 µlamports, every transaction was sent once (`maxRetries: 0`), the next batch waited for `SETTLED` (`finalized` plus the tracker's 15/30/60 s backoff), and MetaMask implements `signAllTransactions` as one popup per transaction.

- **Fee pricing (B-24, D-127).** The user-paid fee transfer requests `USER_FEE_CU_LIMIT = 200 000` compute units. Its price is the 75th percentile of the non-zero `getRecentPrioritizationFees({ lockedWritableAccounts: [the user's USDC account] })`, floored at 16 001 µlamports and capped at 2 500 000 (at most 0.0005 SOL); an RPC error gives the floor. The price is counted in the group's SOL requirement; the plan, which cannot know it, counts the cap (`FEE_TRANSFER_USER_LAMPORTS` = 505 000 lamports). Platform-paid legacy fee legs are unchanged (1 400 000 / 16 001).
- **Rebroadcast (B-25, D-128).** Solana sends use the RPC's default rebroadcast (no `maxRetries`). While the server waits for the fee it also re-sends the fee's identical signed bytes every 2 s. Re-sending the same bytes is not a new transaction; nothing is ever re-signed, rebuilt or replaced, and an unknown outcome is still never re-planned.
- **The next group waits for `confirmed`, not `SETTLED` (B-26, D-129).** A fee leg counts as landed when its signature status is `confirmed` or `finalized` without error. Until then `POST .../groups` answers 409 `OPERATION_IN_PROGRESS` with `details: { reason: "fee_confirming" }`; the web repeats the request every second for up to a minute and shows "Confirming fee…". A plain `OPERATION_IN_PROGRESS` (the fee failed, is `UNKNOWN` or is still being sent) and `TX_MISMATCH` are stops, not retries. Because the next group now starts before the tracker sets `feeCoveredBy`, a leg is covered when `feeCoveredBy` is set or its id is in `routeSummary.covers` of a `network_fee` leg of the same operation that is submitted, pending, unknown or settled (a `FAILED` or released `PLANNED` fee leg covers nothing), so a covered leg is never charged twice. The first tracking backoff for every leg drops from 15 s to 5 s.
- **Sign-and-send tier (B-27, D-130, builds B-07).** On the web, a Solana wallet in `SIGN_AND_SEND_WALLETS = ["MetaMask"]` (the Reown wallet name) that exposes the Wallet Standard `solana:signAndSendTransaction` feature uses tier `sign_and_send`; any other wallet keeps `sign_all` (downgrading to `single`). MetaMask goes from one popup per transaction to **two**: with a fee to charge the first group is the fee transfer alone (it covers the next 12 `PLANNED` Solana asset legs), and the next group, requested once the fee is `confirmed`, is the asset chunk with no fee; a tail whose shares are uncovered again is a fee-only group, then its assets. The flow per group is `POST .../groups` (tier `sign_and_send`), `.../claim` (the legs become `SUBMITTING`, claim before send), the wallet signs AND broadcasts, then `.../sent` reports the signatures (raw 64-byte values from the wallet, base58-encoded by app-core; a subset is accepted). A claim after `sendBy` is 409 `GROUP_EXPIRED`.
  - **Release only on a clear rejection.** `.../release` is called only when the wallet reports a user rejection (nothing was broadcast, or the wallet is the wrong one and was never opened): claimed legs without a signature return to `PLANNED` and no tier downgrade happens. Any other wallet error, or a network failure while reporting, ends `OUTCOME_UNKNOWN` ("Confirming with the network — don't sign again") with the claim kept; the sweep resolves it.
  - **A fee-only group checks what it pays for.** Its fee is not refunded (D-090), so before any fee is charged the wallet must hold the USDC for the fee plus the `amountIn` of every leg it covers, and the SOL for the fee transaction plus those legs' plan-time cost (`INSUFFICIENT_BALANCE` / `SOL_REQUIRED`, nothing formed). This holds for `single` too.
  - **The sweep.** A claim with no signature after 2 minutes: the server first checks whether the prepared blockhash is still valid, then reads the user's signatures newest first in pages of 1 000 (`before`), back past the claim time, for at most 3 pages, and matches landed messages to the prepared ones (equal beyond ComputeBudget; the payer is checked by the tracker's proof). A match sets `sourceTx` and tracking starts. No match is `FAILED` / `NOT_LANDED` only when the blockhash had expired before the lookup AND the pages reached back past the claim; a history too long to read keeps the claim (warning logged, ops check) because the transaction may have landed. A signature the wallet reports after `NOT_LANDED` is refused and written to the audit (`leg.signature_after_not_landed`) for ops. A plan whose only claims ended `NOT_LANDED` still expires. Nothing is resent.
  - **Reported signatures are proven.** A signature the wallet reports is not trusted: before the next group is gated on a fee leg, or a leg is settled or ledgered, the landed transaction must match the prepared one (`landedMatchesPrepared`); failing to fetch it leaves the leg unproven (`fee_confirming`, not final, never covering). A fetched mismatch is 409 `TX_MISMATCH` at the gate. In the tracker a fee leg and an asset leg both become `UNKNOWN` (`TX_MISMATCH_AFTER_SEND`, audit `leg.tx_mismatch_after_send`, `logger.error`; ops resolve): the wallet broadcast it, so money may have moved and failing a fee would charge an honest user again, while an `UNKNOWN` fee still refuses the next group (plain `OPERATION_IN_PROGRESS`), so a forged signature buys nothing. Cost if wrong: ops resolve every fee a wallet rewrote beyond ComputeBudget, and that investment waits for them.
  - **A reported signature that never lands.** `/sent` stores the prepared blockhash (the proof accepts no other) and the report time. The tracker fails the leg once that blockhash expired and 2 minutes passed since the report (a wallet that rebuilt the blockhash at approval may still land a copy until then); a failed fee covers nothing, so the user can retry. A released claim goes back to the plan's minimums (the claim lowered them when the user accepted new prices).
  - **Accepted limits.** The list is extended from `group.quoted` telemetry; the 2-popup flow and the proof against a real RPC response still need a device check (OPEN-ITEMS).

### Rulings made while building P1
- **Needs-action only for grouped operations.** An operation without a group keeps today's terminal rules (`PARTIAL` or `FAILED` on a failed leg), so mobile behaves as before. Cost if wrong: mobile users see `PARTIAL` after a failure, as today.
- **Per-leg exclusivity.** An operation that has any `operation_groups` row refuses per-leg quote and submit for its buys (409 `INVALID_TRANSITION`, "Continue this investment on the website."), and a group request is refused if any leg left `PLANNED` through the per-leg path or a candidate leg is a legacy `platform_fee_payer` one. A recovery leg (`recoveryOf`, D-096) is the exception: it is a separate per-leg path outside the groups, quoted and submitted on its own while the other legs wait for the user (it waits only for nothing to be in flight), and the website shows its "Complete swap" button.
- **Groups are invest-only in P1.** Fee shares exist only on invest legs and a sell puts its fee last. Sell, repair and rebalance keep the per-leg flow; the website shows them the Stop/Continue banner when another operation needs action.
- **The plan's fee leg is reused by the first group**, so a plan with a fee never leaves a second fee leg behind; charges are written per fee leg, with the old rows backfilled.
- **The tier.** The plan request and every group request carry the tier the wallet will sign with: `sign_and_send` for a listed wallet with the Wallet Standard feature (P1b), otherwise `sign_all` (the plan's tier only sets the estimate on the review step), and the website downgrades to `single` for the session when the wallet answers "not supported"; a cancelled popup never downgrades. When a plan request has no tier the API assumes `single` (mobile's estimate), not `sign_all`. The tier chooses the response shape, the size of a group (`single` forms small groups, above) and the approvals estimate; security never depends on it. A wallet known to lack batch signing starts at `single` before the quote; one that answers "not supported" at signing gets a fresh `single` group.
- **Group quotes count against the quote rate limit.** A group request consumes one point per transaction (`K_SIGN_ALL`) of the 60 per minute quote limiter.
- **Spec 11 still applies.** The RWA re-evaluation runs for every leg of a group at quote time.
- **D-073 stays waived for the pilot.** The fresh quote is accepted and the stored floor lowered at the claim (when the user signs), never at the quote, so a group left unsigned cannot hide the explicit "Accept new prices" tap from the next one; when a fresh minimum is below the plan's, the website holds the wallet behind that tap (disabled once the quotes expired).
- **The network fee covers EVM gas drops only.** Solana gas and the Bitcoin miner fee (paid from the PSBT's inputs) are the user's; neither is charged. An EVM gas drop waits for the operation's fee leg only when it has one.
- **Legacy legs.** Legs planned before this release keep `platform_fee_payer` (`svmSponsor`, co-sign, reservations) until P4.

## Alternatives considered
- Keep per-leg signing and only pay the gas differently: still one popup per leg.
- Sign-and-send (the wallet broadcasts, B-07) for every wallet: fewer wallets support it and the server loses control of order and the blockhash gate. Built in P1b (B-27) only for wallets where `signAllTransactions` costs one popup per transaction (MetaMask); everyone else keeps sign-only.
- One merged transaction for the fee plus swaps: LI.FI does not return a merged multi-swap, and size, compute and account limits would force a custom builder (FUTURE-PLANS).
- A platform SOL top-up instead of user-paid gas: platform float, caps and an abuse surface for no gain (D-094 stays).

## Consequences
### Positive
- Up to 11 assets are one wallet approval with the fee in the same popup, then about one approval per 11 assets.
- The platform no longer funds, caps or reserves Solana gas, and the wallet-rewrite `TX_MISMATCH` problem for the fee payer is gone.
- A failure leaves a usable investment with a clear next step instead of a dead `PARTIAL`.

### Negative / trade-offs
- The user needs SOL (a few thousandths per basket: signatures and priority fees, plus about 0.002 SOL for each token account that has to be created, and a 0.001 SOL buffer) and gets `SOL_REQUIRED` without it.
- Fees are charged per batch, so a user who stops after a sent fee has paid part of the fees (D-090; legal review OPEN).
- An operation needing action blocks new plans for up to 24 h (one open operation per user); the website shows a Stop banner on every entry point.
- A blockhash lives about 60 s: a large chunk with a slow wallet can expire (`GROUP_EXPIRED`, one more popup).
- Sign-and-send gives up server control of order and of the blockhash gate; the wallet broadcasts, so a wallet that fails after broadcasting leaves the outcome to the sweep and tracker (never to a resend) and a user may wait a few minutes (P1b).

### Security, financial and operational impact
- The server verifies every transaction before claiming any; a signed set that differs from the quoted set, includes a foreign leg or changes the fee payer or any non-ComputeBudget instruction is refused whole (409 `TX_MISMATCH`) with nothing sent.
- Claim before send; two concurrent submits of the same group send once; an unknown send outcome becomes `SUBMITTED` and is tracked, never resent.
- The USDC balance is rechecked at group quote; a short wallet is refused (`INSUFFICIENT_BALANCE` with `usdcRequiredMicro`) or caught at preflight, which releases every claim. A later chunk checks the finalized balance, which may still include USDC that an earlier chunk's buys have not spent yet.
- Telemetry: the website sends the wallet name and tier with the group request; the server logs `group.quoted { walletName, chain, tier, legs, approvals }` and never an address.

## Migration / rollout
Migration `0025_signing_groups.sql`: `operation_groups`, `operation_fee_charges` (backfilled from `operation_fees`), new leg and operation columns, and `gas_payer` gains `user_solana`. The runtime role gets SELECT, INSERT and UPDATE only. New Solana legs are `user_solana` from deploy; plans created before it keep the co-sign path until P4 retires `svmSponsor`, `sponsorExposure`, `SOLANA_FEE_PAYER_SECRET` and the Solana caps.

## Validation
API integration tests with mocked chain and LI.FI (groups, Continue, auto-stop, user-paid gas, fee charges, fee pricing, rebroadcast, confirmed gating, the coverage rule, claim / sent / release, the sweep and its paging, signature proof, mismatched and never-landing fees, fee-only funding), validator tests for `feeShares` and `approvalsEstimate`, app-core tests for the group signer (sign-and-send, release, `OUTCOME_UNKNOWN`, fee-confirming retry), web tests for the review, prices strip, needs action, banner, MetaMask sign-and-send, "Confirming fee…" and the signer's tier choice. Mobile Solana signing with user-paid SOL is not device-tested yet.
