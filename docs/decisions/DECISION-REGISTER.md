# Architecture Decision Register

**Status key:** `APPROVED` = explicit direction in supplied project material; `PROPOSED` = current architecture direction but not fully locked; `OPEN` = requires product/technical decision.

| ID | Topic | Current direction | Status / notes |
|---|---|---|---|
| D-001 | User identity | User account is distinct from wallet addresses and organization identity. | APPROVED in supplied auth/onboarding specs |
| D-002 | Normal user wallet model | One active investment wallet per normal user, with chain accounts/addresses associated to it; additional independent wallets are a separate concept. | APPROVED in supplied auth flow; preserve its exact constraints |
| D-003 | Wallet authentication | Reown AppKit for wallet connection; backend verifies SIWE (EVM) / SIWS (Solana) signatures and issues backend-managed sessions. Supabase is PostgreSQL only, not the session issuer. | APPROVED by user 2026-09-29 (supersedes "Supabase session" in `docs/source/User-Authentication-Flow.txt`); ADR-003 |
| D-004 | Manager onboarding | Public application (email-confirmed) → platform screening in the ops area → `SCREENING_APPROVED` → applicant signs in with the exact submitted wallet (a typed address is an identifier only and never creates or links a user) → `create_manager_organization` permission granted at sign-in/add-chain, or immediately at approval if a proven user already owns the address → user creates org → platform verifies org. | APPROVED; refined by user 2026-09-30 (hybrid wallet proof, supersedes the pending-user step of the supplied onboarding flow); ADR-007 |
| D-005 | Organization as durable manager entity | Organization owns/represents basket business context; membership grants user authority. Lifecycle `DRAFT → SUBMITTED → UNDER_REVIEW → VERIFIED` (with `CHANGES_REQUIRED → RESUBMITTED`, `REJECTED`); content lives in versions (one open version, whole-profile change requests once verified); one owned non-rejected organization per creator; the creator becomes `OWNER`. Membership grants authority: only an `ACTIVE` membership carries permissions (D-048), memberships follow one lifecycle (`PENDING_WALLET_VERIFICATION`, `INVITED`, `PENDING_DOCUMENTS`, `UNDER_REVIEW`, `CHANGES_REQUIRED`, `ACTIVE`, `REJECTED`, `REMOVAL_REQUESTED`, `REVOKED`), only `VERIFIED` organizations invite, there is always exactly one `OWNER`, and removal or leaving keeps the member's history. | APPROVED in supplied onboarding flow; refined 2026-09-30; ADR-008, ADR-009 |
| D-006 | Payout wallet | Separate organization payout resource, not the personal/authentication wallet. It is `VERIFIED` only after a Solana signature over a payout-specific challenge bound to organization, address and session user; typed addresses never verify. Replacement needs a new signature plus ops approval and the old wallet stays active until approval; changes are refused while the organization is under review. History is kept. | APPROVED in supplied onboarding flow; refined 2026-09-30; ADR-008 |
| D-007 | Basket creation | A basket starts as `DRAFT` with a draft version 1, is validated server-side (stable issue codes, nothing normalized silently) and submitted for platform review. Approval leaves the version `approved`; the manager then publishes it. A basket is not public or investable before publication, and nothing is investable in this release. | APPROVED in supplied basket spec; implemented in Spec 6; ADR-011 |
| D-008 | Basket versioning | Content lives in immutable-once-submitted versions: one open version, frozen at submit, hashed, publish refused if the approved hash differs, published versions never edited, the previous published version becomes `superseded`. A change is a new version with a required rationale and a computed diff; version history is public. | APPROVED direction; implemented in Spec 6; ADR-011 |
| D-009 | Asset scope | Initial scope: crypto, stablecoins and approved RWAs recorded in the registry (ADR-010). Asset chains are `ASSET_CHAINS` (D-053), independent of the auth chains (D-032); recording a chain does not make it executable. Future categories remain future scope. | APPROVED scope; implemented in Spec 5; executable chains decided per execution spec |
| D-010 | Universal asset model | Separate economic instrument, chain deployment and execution route, plus eligibility rules and price references attached to the instrument. A deployment is never interchangeable with another; one non-retired deployment per `(chain, address)` registry-wide. | APPROVED; implemented in Spec 5; ADR-010 |
| D-011 | Asset approval | Assets are onboarded by ops only (managers cannot propose in release 1). An `ops_reviewer` drafts, edits and submits; only an `ops_admin` decides and runs lifecycle actions; the admin who submitted cannot decide. Managers select only `ACTIVE` registry entries; arbitrary addresses cannot become investable. | APPROVED; implemented in Spec 5; ADR-010 |
| D-012 | Chain data | Alchemy is the selected provider for supported RPC/event/data needs; adapter boundary is recommended. | PROPOSED/selected stack; verify coverage per chain |
| D-013 | Swap routing | 0x for supported swap and cross-chain routes; support is route-specific. | PROPOSED; verify current provider coverage and terms |
| D-014 | Native Bitcoin | Separate Bitcoin adapter for native BTC and UTXO behavior. | PROPOSED |
| D-015 | Pricing | CoinMarketCap is the primary crypto market-data provider: on demand, batched, Redis 60 s, stale flag after 5 min, optional key (missing key or failure = `unavailable`), no history. | IMPLEMENTED in Spec 5 (ADR-002); verify plan, terms and response shape with a real key |
| D-016 | RWA data | CoinMarketCap plus issuer-specific data initially; RWA.xyz optional if deeper coverage is needed. | PROPOSED |
| D-017 | Persistence | Supabase PostgreSQL with Drizzle ORM/migrations; schema, client and migrations live in `packages/db` (`@repo/db`). | SELECTED by user; ADR-006 |
| D-018 | Cache/jobs | Redis for rate limits and transient cache. Scheduled database jobs run inside Postgres with `pg_cron`; BullMQ is not used until a real queue is needed. PostgreSQL remains the durable source of truth. | APPROVED; ADR-006 |
| D-019 | Object storage | Cloudflare R2, private bucket. Owner uploads use a presigned direct PUT to `incoming/` (expired by a 1-day lifecycle rule) followed by a server-side confirm step; verified files live under `documents/`; downloads are ops-only short-lived presigned GETs. No malware scanner in release 1. | SELECTED in stack discussion; detailed 2026-09-30; ADR-008 |
| D-020 | Backend shape | Node.js + Express + TypeScript, modular monolith initially. Flat `apps/api/src` (`app.ts`, `server.ts`, `env.ts`, `middleware/`, `routes/`, `services/`, `providers/`). Errors are `http-errors` with a stable `code`; logging is winston via `@repo/logger`; env is validated with envalid. Internal packages export TypeScript source. | SELECTED; ADR-006 |
| D-021 | Frontend | Next.js (App Router) + React, Tailwind v4, shadcn/ui; Motion and 3D only selectively. Expo for mobile. Turborepo + pnpm monorepo. | SELECTED |
| D-022 | Physical custody/accounting model | Options include user wallet, delegated authority, per-user vault or shared vault. Shared physical positions require logical sub-ledgers and coordinated netting. | OPEN — lock before execution/accounting implementation |
| D-023 | Shared asset shortage policy | Must explicitly define restore, accept/reallocate, customization and allocation attribution. | OPEN |
| D-024 | Spend authority | Chain-specific authority/delegation design must define assets, limits, duration, revocation and signing model. | OPEN/track in dedicated authority ADR |
| D-025 | Eligibility | Evaluate user + instrument + provider + route + jurisdiction + action; not one global KYC boolean. | APPROVED architectural direction; legal policy values open |
| D-026 | RWA execution | Per-instrument routes may include subscription, secondary market, transfer or redemption; async settlement must be modeled. | OPEN per instrument/provider |
| D-027 | Pricing hierarchy | Market price (CoinMarketCap) and issuer NAV (ops-entered) are distinct entries and never merged; freshness is flagged after 5 min. Source priority, fallback between providers, indicative prices and executable quotes remain to be defined. | PARTIAL (Spec 5); hierarchy still OPEN |
| D-028 | Rebalance and Fix semantics | Distinguish reconciliation, repair, rebalance and customization; no silent asset movement. A rebalance is a manager-proposed new basket version (required rationale, same review and publication); `reviewFrequency` and drift threshold are disclosures only, never automatic rules, and user consent to apply it is always explicit (platform notice). | APPROVED principle; version/consent side implemented in Spec 6 (ADR-011); execution and Fix policies open |

| D-029 | Platform name | Bytesac. | APPROVED by user |
| D-030 | Initial settlement currency | USDC on Solana; design for future expansion to additional currencies. | APPROVED by user |
| D-031 | Sessions | Opaque 32-byte token, HMAC-hashed at rest. Web: httpOnly cookie via same-origin Next proxy, 12 h idle / 7 d absolute. Mobile: bearer in secure storage (sent with header `X-Client: mobile`), 7 d idle / 30 d absolute. No rotation on renewal; rotation on security events (add chain account); a revoked session cannot be rotated. DB-time expiry checks. | APPROVED; ADR-003 |
| D-032 | Release-1 auth chains | Solana (SIWS) + EVM (SIWE) on Ethereum, Base, BNB Chain, Arbitrum. | APPROVED |
| D-033 | Chain-account association | Verification method decides scope: ECDSA-recovered EOA proof registers all supported EVM chains; ERC-1271/6492 register only the verified chain (RPC transport failure is retryable `VERIFIER_UNAVAILABLE`, never an invalid signature); cross-family additions only via explicit logged-in "Add chain account" (serialized per wallet); different same-family address refused. | APPROVED; ADR-004 |
| D-034 | OTP providers | Email via Resend (idempotency key per verification) with backend-generated HMAC-hashed OTP; SMS via Twilio Verify. Behind provider modules in `apps/api/src/providers`. | APPROVED |
| D-035 | API contracts & topology | Zod schemas in `packages/validator` (`@repo/validator`, re-exports zod); typed `packages/api-client`; client logic shared by web and mobile in `packages/app-core`; web calls the API through a same-origin Next rewrite; API sends no CORS headers. Challenge request body is `{ purpose, chain, address }` (chain family derived from chain). | APPROVED |
| D-036 | Test runner | Vitest (+ Supertest; `jest-expo` for mobile smoke tests). | APPROVED |
| D-037 | Sign-in challenge lifecycle | `pending → processing (30 s lease) → consumed / rejected`; no transaction held during RPC; consumption atomic with account linking and session creation. | APPROVED |
| D-038 | Database access model | Backend-only DB access; schema `app` not exposed via Supabase Data API; role `bytesac_api` (DML, no DELETE), retention as `app.purge_expired()` run by pg_cron under the schema owner (no separate role), migrations by schema owner (Supabase `postgres`; local superuser); RLS enabled with role-scoped permissive policies (no `BYPASSRLS`); default privileges revoked from PUBLIC/anon/authenticated. | APPROVED; ADR-005, ADR-006 |
| D-039 | Wallet unlink & recovery (release 1) | No user-initiated unlink; ops-only audited disable/reactivate; recovery via future wallet migration. | APPROVED |
| D-040 | Data retention | Challenges 7 days after expiry (except those referenced as address or payout wallet evidence); sessions, contact verifications and application email codes 90 days after they are resolved, unconfirmed (`EMAIL_PENDING`) manager applications 24 h after creation together with their codes and events (purged daily at 03:00 UTC by pg_cron); audit events 7 years proposed. | APPROVED except audit period: OPEN pending compliance |
| D-041 | Mobile wallet stack | Reown AppKit React Native 2.0.6 with wagmi adapter (wagmi 2.19.5, `@wagmi/connectors` 6.2.0 pinned via root override) for EVM; Solana adapter with Phantom/Solflare; session token in `expo-secure-store`; `jest-expo` tests. Bundles and type-checks on Expo 57 / RN 0.86 (`expo export` OK). | APPLIED; on-device wallet connect/sign compatibility PENDING user verification |
| D-042 | Ops surface and platform roles | Minimal ops area in the web app (`/ops`); staff sign in with a wallet and hold a platform role (`ops_reviewer`, `ops_admin`; admin implies reviewer) in `platform_roles`. Roles are read from the database on every request; admins grant/revoke in the UI (last admin cannot be revoked); first admin via CLI `ops:grant-role`. Every ops action is audited. | APPROVED 2026-09-30; ADR-007 |
| D-043 | Applicant communication | Contact happens outside the app. Ops records status, internal notes and an optional message to the applicant. The applicant gets status emails (Resend) and a private status page reached by a secret link (32-byte token, HMAC-hashed at rest, carried in the URL fragment and an `X-Application-Token` header) with one reply when additional information is requested. | APPROVED 2026-09-30; ADR-007 |
| D-044 | Application abuse protection | Mandatory email confirmation (6-digit code) before an application enters the ops queue; rate limits per IP and per email; no captcha in release 1. Unconfirmed applications are purged after 24 h by `app.purge_expired()`. | APPROVED 2026-09-30; ADR-007 |
| D-045 | Verification requirement templates | Required fields and documents per organization type come from table `verification_requirement_templates` (seeded; most specific type + jurisdiction wins; retired rows ignored; catalog keys only). No editor UI in release 1. | APPROVED 2026-09-30; ADR-008 |
| D-046 | Whole-profile versioning | Public and private organization content is versioned as a whole. Submit moves the draft to `in_review`; approval switches the current public version and supersedes the previous one; the public profile never shows pending content. | APPROVED 2026-09-30; ADR-008 |
| D-047 | Document safety | PDF, JPEG and PNG only, at most 10 MB, declared type and size signed into the upload and re-checked with magic bytes on confirm, stored `not_scanned`, attachment-only ops downloads (member reviewers refused), document links soft-unlinked (`removed_at`) because the runtime role has no DELETE. | APPROVED 2026-09-30; ADR-008 |

| D-048 | Organization permission matrix | One fixed matrix `ROLE_PERMISSIONS` in `@repo/validator` (`org.read`, `org.edit`, `payout.manage`, `members.manage`, `members.manage_admins`, `analytics.read`, `baskets.manage` across OWNER, ADMIN, MANAGER, ANALYST, VIEWER), shared by API and web; the server checks it on every organization route and only `ACTIVE` memberships grant permissions. Not configurable per organization in release 1. | APPROVED 2026-09-30; ADR-009 |
| D-049 | Member verification for reviewed roles | `ADMIN` and `MANAGER` become `ACTIVE` only after ops approve the member's own verification (fields and documents from the `member` template; visible to the member and ops, the organization sees only the status). `ANALYST` and `VIEWER` need wallet proof and acceptance only. A role upgrade keeps the old role until approval. Only an approval of the current membership counts: a re-invite after leaving, an upgrade and an ownership-transfer target are not satisfied by an approval of a past membership. | APPROVED 2026-09-30; ADR-009 |
| D-050 | Ownership transfer | Ops-only: an `ops_admin` transfers ownership in `/ops` to an active member with an approved verification, with a reason; the old owner becomes `ADMIN`; audited; exactly one `ACTIVE` `OWNER` is enforced by a partial unique index. Owners contact support, there is no self-service transfer. The target's approval must belong to the current membership. | APPROVED 2026-09-30; ADR-009 |
| D-051 | Public team | Opt-in: a member's public name (and optional title) shows with role and dates under current and former members on a verified organization's public profile; wallets, emails and ids are never shown. | APPROVED 2026-09-30; ADR-009 |
| D-052 | Invite linking by wallet proof | An invitation names a wallet and email; a typed address never links, creates or activates anyone. The invite becomes `INVITED` only when the wallet is proven in the Spec 1 sign-in or add-chain transaction (EOA and ed25519 on any chain of the family, ERC-1271/6492 on the invited chain only; disabled addresses and non-active users never link). Invites expire after 14 days, checked on read and accept. | APPROVED 2026-09-30; ADR-009 |
| D-053 | Asset chains | `ASSET_CHAINS`: `solana`, `ethereum`, `base`, `bnb`, `arbitrum`, `polygon`, `bitcoin`, separate from the auth `CHAINS`. On-chain verification only for ethereum, base, bnb, arbitrum (ERC-20) and solana (SPL); the rest are manual with a source URL. | APPROVED 2026-09-30; ADR-010 |
| D-054 | Deployment verification | EVM metadata via Alchemy/viem, Solana mint decimals via Alchemy `getTokenSupply`, manual otherwise; a mismatch or non-token blocks submit and approval; transport failure is 503 `VERIFIER_UNAVAILABLE` and stores nothing; verify only on `DRAFT` on-chain deployments, 30/h per ops user; no scheduled re-verification. | APPROVED 2026-09-30; ADR-010 |
| D-055 | Asset lifecycle and per-item review | The instrument is the review unit (`DRAFT → UNDER_REVIEW → APPROVED | CHANGES_REQUIRED → ACTIVE ⇄ PAUSED → DEPRECATED → RETIRED`); items added later need admin approval and activation; identity fields lock once approved; edits are refused while `UNDER_REVIEW` or `RETIRED`; retiring an instrument retires its deployments and routes; history is never deleted. | APPROVED 2026-09-30; ADR-010 |
| D-056 | Session asset read API | Signed-in users read only `ACTIVE` instruments and `ACTIVE` items through an explicit allow-list (`GET /v1/assets`, `/v1/assets/:id`); never rules, review messages, internal notes, observed metadata or actor ids. | APPROVED 2026-09-30; ADR-010 |
| D-057 | Basket access flags | Org `baskets.manage` plus per-basket assignments (`lead`, `co_manager`) with flags `edit`, `submit`, `publish`, `lifecycle`, `assign`; a lead holds all five, a co-manager defaults to `edit`, `submit`; OWNER/ADMIN act on every basket, `org.read` reads all read-only; the assignment's membership must stay `ACTIVE` with `baskets.manage`. Enforced server-side per action. Assignment lockdown: nobody changes their own flags or ends their own lead role (ending one's own co-manager assignment, i.e. leaving, stays allowed); only OWNER, ADMIN or the current ACTIVE lead add, replace or end a lead assignment; a co-manager holding `assign` only adds, edits and ends other co-manager assignments. Retired and rejected baskets take no decisions, withdrawals or assignment changes. | APPROVED 2026-10-01 (assignment lockdown decided 2026-10-01 after final review); ADR-011 |
| D-058 | Basket fee caps | Percent fees 0 to 100 bps; every fixed fee and the subscription amount at most 1% of the minimum investment, compared exactly as micro-USDC integers; amounts are `DecimalString` (6 decimals). Fees are disclosed terms only: nothing is charged. Exact caps await confirmation. | APPROVED 2026-10-01; ADR-011; caps OPEN for confirmation |
| D-059 | Disclosure templates | Mandatory platform notices are ops-managed templates (seeded; new version retires the previous active one), chosen by asset types, pinned to each version at submit, re-pinned at publish if changed, and never removable by managers. Wording is placeholder pending compliance. | APPROVED 2026-10-01; ADR-011; copy OPEN |
| D-060 | Manager-leaves policy | A membership that stops being eligible ends its basket assignments automatically (history kept); a published basket without an active lead becomes `REASSIGNMENT_REQUIRED`; a new lead is `PENDING_APPROVAL` until an `ops_admin` approves, while the current lead stays active until then. | APPROVED 2026-10-01; ADR-011 |
| D-061 | Public basket pages | `/baskets` and `/baskets/[slug]` need no sign-in and show published content only (never drafts, reviews, internal notes, ids, wallets or emails), with status notices, prices (stale or unavailable), version history with diffs and manager history; old slugs redirect permanently; `RETIRED` is served but not listed; the organization profile lists its baskets; the invest button is disabled. | APPROVED 2026-10-01; ADR-011 |

## How to update
When a decision is explicitly locked, update the status and add an ADR for consequential architecture decisions. Retain superseded decisions for traceability.
