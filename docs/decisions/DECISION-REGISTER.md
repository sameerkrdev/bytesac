**Status key:** `APPROVED` = explicit direction in supplied project material; `PROPOSED` = current architecture direction but not fully locked; `OPEN` = requires product/technical decision.

|---|---|---|---|

| D-002 | Normal user wallet model | One active investment wallet per normal user, with chain accounts/addresses associated to it; additional independent wallets are a separate concept. | APPROVED in supplied auth flow; preserve its exact constraints |

| D-005 | Organization as durable manager entity | Organization owns/represents basket business context; membership grants user authority. Lifecycle `DRAFT → SUBMITTED → UNDER_REVIEW → VERIFIED` (with `CHANGES_REQUIRED → RESUBMITTED`, `REJECTED`); content lives in versions (one open version, whole-profile change requests once verified); one owned non-rejected organization per creator; the creator becomes `OWNER`. | D-006 | Payout wallet | Separate organization payout resource, not the personal/authentication wallet. It is `VERIFIED` only after a Solana signature over a payout-specific challenge bound to organization, address and session user; typed addresses never verify. Replacement needs a new signature plus ops approval and the old wallet stays active until approval; changes are refused while the organization is under review. History is kept. | APPROVED in supplied onboarding flow; refined 2026-09-30; ADR-008 |
| D-007 | Basket creation | A basket starts as `DRAFT` with a draft version 1, is validated server-side (stable issue codes, nothing normalized silently) and submitted for platform review. Approval leaves the version `approved`; the manager then publishes it. A basket is not public or investable before publication, and nothing is investable in this release. | APPROVED in supplied basket spec; implemented in Spec 6; ADR-011 |
| D-008 | Basket versioning | Content lives in immutable-once-submitted versions: one open version, frozen at submit, hashed, publish refused if the approved hash differs, published versions never edited, the previous published version becomes `superseded`. A change is a new version with a required rationale and a computed diff; version history is public. | APPROVED direction; implemented in Spec 6; ADR-011 |
| D-009 | Asset scope | Initial scope: crypto, stablecoins and approved RWAs recorded in the registry (ADR-010). Asset chains are `ASSET_CHAINS` (D-053), independent of the auth chains (D-032); recording a chain does not make it executable. Future categories remain future scope. | APPROVED scope; implemented in Spec 5; executable chains decided per execution spec |
| D-010 | Universal asset model | Separate economic instrument, chain deployment and execution route, plus eligibility rules and price references attached to the instrument. A deployment is never interchangeable with another; one non-retired deployment per `(chain, address)` registry-wide. | APPROVED; implemented in Spec 5; ADR-010 |
| D-011 | Asset approval | Assets are onboarded by ops only (managers cannot propose in release 1). An `ops_reviewer` drafts, edits and submits; only an `ops_admin` decides and runs lifecycle actions; the admin who submitted cannot decide. Managers select only `ACTIVE` registry entries; arbitrary addresses cannot become investable. | APPROVED; implemented in Spec 5; ADR-010 |
| D-012 | Chain data | Alchemy is the selected provider for supported RPC/event/data needs, behind adapters: EVM and Solana RPC (balances, receipts, finality) and, since Spec 8, the Bitcoin UTXO (Blockbook-compatible) REST API for balance, transaction and broadcast. | PROPOSED/selected stack; verify coverage per chain; Alchemy Bitcoin `/tx` and `/sendtx` response shapes are a pre-launch check (ADR-014) |
| D-013 | Swap and cross-chain routing | LI.FI is the only route provider, behind a `RouteProvider` abstraction (`connections`, `quote`, `status`; selection by `ROUTE_PROVIDER_ORDER`, default `lifi`) so Spec 11 can add providers. It quotes same-chain swaps and cross-chain legs (Solana, EVM, native BTC) delivered to the user's own linked address; every quote is validated against the leg (tokens, chains, `toAddress`, minimum output). 0x is not used. | APPROVED (ADR-014); real-key checks (`toAddress` echo, `svmSponsor`, Solana and Bitcoin transaction encodings, terms, limits) are pre-launch |
| D-014 | Native Bitcoin | Separate Bitcoin adapter for native BTC and UTXO behavior. | PROPOSED |
| D-015 | Pricing | CoinMarketCap is the primary crypto market-data provider: on demand, batched, Redis 60 s, stale flag after 5 min, optional key (missing key or failure = `unavailable`). | D-016 | RWA data | CoinMarketCap plus issuer-specific data initially; RWA.xyz optional if deeper coverage is needed. | PROPOSED |
| D-017 | Persistence | Supabase PostgreSQL with Drizzle ORM/migrations; schema, client and migrations live in `packages/db` (`@repo/db`). | SELECTED by user; ADR-006 |

Retention keeps running inside Postgres with `pg_cron`. PostgreSQL remains the durable source of truth; jobs never move money or touch user balances. | APPROVED; ADR-006 (rewritten 2026-10-01), ADR-012 |

| D-020 | Backend shape | Node.js + Express + TypeScript, modular monolith initially. Flat `apps/api/src` (`app.ts`, `server.ts`, `env.ts`, `middleware/`, `routes/`, `services/`, `providers/`). | D-021 | Frontend | Next.js (App Router) + React, Tailwind v4, shadcn/ui; Motion and 3D only selectively. Expo for mobile. Turborepo + pnpm monorepo. | SELECTED |
| D-022 | Physical custody/accounting model | Self-custody: assets always sit in the user's own Solana investment wallet and linked EVM addresses; the platform holds no keys, funds or in-transit assets and runs no vaults. Basket positions are a logical sub-ledger (user × basket × deployment, raw base units) reconciled against on-chain balances. Investments are funded with USDC on Solana; constituents may live on any supported chain (native BTC excluded in release 1). | APPROVED 2026-10-01; ADR-013 |
| D-023 | Shared asset shortage policy | A wallet shortfall versus combined basket quantities (or basket cash versus wallet USDC on Solana) is allocated pro-rata across the baskets holding it by default (`SHORT`), and the affected baskets cannot be rebalanced until it is resolved. The user resolves it per asset: **Buy back** (one repair plan for the whole deployment, funded with free USDC) or **Sync** (no transaction; the user edits the split across the baskets, which must sum exactly to the shortfall and may not exceed any basket's record). Basket cash can only be synced. Surplus is outside baskets and never touched. No quantity is counted twice; nothing is restored automatically. | APPROVED 2026-10-01; user-editable split 2026-10-02; ADR-013, ADR-015 |
| D-024 | Spend authority | No delegation in release 1: every transaction is signed by the user against a reviewed plan of legs (60 s quotes, on-chain minimum output, user slippage default 1% max 3%, exact-amount EVM approvals). Sign-in, publication or earlier approvals never authorize spending. Delegated signing needs a future ADR. | APPROVED 2026-10-01; ADR-013 |
| D-025 | Eligibility | Eligibility is evaluated per user, instrument, route, jurisdiction, investor status and action by a pure engine (`evaluateEligibility`); there is no global KYC flag. RWAs are denied by default; the most specific matching rule wins and the strictest outcome wins within a tier; every RWA leg stores its decision. Legal policy values (the rules themselves) are entered by ops from provider terms and are open. | APPROVED 2026-10-03; ADR-018; rule values open |
| D-026 | RWA execution | Release 1 offers only permissionless secondary-market RWA tokens bought and sold through LI.FI like crypto (route method `swap` or `secondary_market`, synchronous). Issuer subscription, redemption and asynchronous settlement are future plans and are never offered. | APPROVED 2026-10-03; ADR-018 |
| D-027 | Pricing hierarchy | Market price (CoinMarketCap) and issuer NAV (ops-entered) are distinct entries and never merged; freshness is flagged after 5 min. Simulated model performance uses only the daily CoinMarketCap USD snapshots (an instrument without a market price reference has no snapshots, so a basket holding it has no performance); a missing day repeats the last price and marks a gap, and more than 3 days of gap or stale data makes performance unavailable. Source priority, fallback between providers, indicative prices and executable quotes remain to be defined. | PARTIAL (Spec 5, Spec 7); hierarchy still OPEN |
| D-028 | Rebalance and Fix semantics | Reconciliation, repair, rebalance and customization are distinct; no silent asset movement. A rebalance is a manager-proposed new basket version (required rationale, same review and publication); `reviewFrequency` and drift threshold are disclosures only, never automatic rules. A holder applies or skips it with explicit consent: apply plans from current reconciled holdings to the latest version (skipped versions are never replayed) and changes the applied version only when the operation completes; skip changes nothing in the wallet. Weight drift offers Rebalance to the applied version (while it is current) or Keep custom. Repair (buy back) and sync resolve a shortfall (D-023). | APPROVED; versions in Spec 6 (ADR-011); execution, skip, drift, keep custom and repair in Spec 9 (2026-10-02; ADR-015) |

A plan is refused while a platform wallet cannot fund it (D-072). `PARTIAL` and `FAILED` operations are terminal; nothing is retried automatically. | APPROVED 2026-10-01; ADR-014; cap values and KMS OPEN |
| D-069 | Investability and eligibility | A basket is investable when it is `ACTIVE` with a published version and every constituent is investable: an `ACTIVE` instrument with an `ACTIVE` deployment and an `ACTIVE` execution route whose provider is enabled, a LI.FI connection from USDC on Solana (cached 1 h), and Bitcoin constituents `native`. An RWA (`TOKENIZED_*`) additionally needs a deployment that is not `permissioned`, a route with method `swap` or `secondary_market`, and an `ACTIVE` CoinMarketCap market price (reasons `RWA_PERMISSIONED`, `RWA_ROUTE_UNSUPPORTED`, `RWA_PRICE_REQUIRED`). A user is eligible with a verified email and phone, a linked address for each chain family the basket needs (Solana is the investment wallet), no other `PLANNED`/`IN_PROGRESS` operation (one per user, partial unique index) and, for each RWA constituent, an `ALLOWED` engine outcome for `acquire` (`NOT_ELIGIBLE_ASSET`, or `DECLARATION_REQUIRED` without a current declaration). The amount must meet the minimum and increment and the USDC balance. Reasons are reported per instrument; the web shows each with an action link. | APPROVED 2026-10-01; RWA rules 2026-10-03; ADR-014, ADR-018 |
| D-070 | Position ledger and reconciliation | A position is an append-only sub-ledger (`position_ledger_entries`, raw base units, signed) written when a leg settles with the amount actually received; closed positions keep their ledger as the former-basket record. Reconciliation (nightly and on portfolio read, at most once a minute per user) compares wallet balances with the summed ledger and appends `OK`/`SHORT`/`SURPLUS` rows; shortfalls are pro-rata (D-023) and display only until Spec 9. Sell quantity is `min(ledger x percent, wallet balance)`; exits do not depend on route status. Unknown leg outcomes are re-checked hourly for 7 days and never resubmitted. | APPROVED 2026-10-01; ADR-014 |

## Spec 8 review fixes (2026-10-01, decided by the product owner)

| ID | Decision | Detail | Status |
|---|---|---|---|
| D-071 | Sell fee order, UNKNOWN legs, claim before send | Sell network fee: first leg when the user holds at least the fee in USDC on Solana; otherwise last (an unpaid fee is an accepted loss within the caps) but only for Solana-only sells: a sell that includes an EVM asset is refused at plan time with 409 INSUFFICIENT_BALANCE until the wallet holds the fee in USDC (binding user decision, supersedes the earlier ruling). The user may stop an operation while a leg is `UNKNOWN` (it becomes `PARTIAL`; the leg keeps being tracked and ledgered). Dropped Solana transactions become `FAILED` through blockhash expiry; legs with nothing visible keep rechecking and the recheck chain survives provider errors. Ops resolve tool `POST /v1/ops/operations/:id/legs/:legId/resolve` (`ops_admin`, audited, verifies on-chain evidence). A leg is claimed (`SUBMITTING`, unique per chain and transaction id) before anything is sent. | APPROVED 2026-10-01; ADR-014 |
| D-072 | Gas budget lifecycle and sponsor exposure | Unspent reservations are released when an operation is cancelled or expires; EVM drops always only after the operation's network fee leg has settled, recorded under the operation lock only while it is open; a sweeper cancels expired untouched plans (releasing reservations) and turns orphaned SUBMITTED or PENDING_CHAIN legs UNKNOWN; at most 5 drops per user per chain per day. Token-account rent paid by the fee payer is counted in the reservation and the network fee. The fee payer co-signs only transactions where it is the payer at index 0, referenced by no instruction except as ATA `CreateIdempotent` funder, with a capped priority fee and bounded size. Plans are refused while a platform gas wallet cannot fund them. | APPROVED 2026-10-01; ADR-014 |
| D-073 | Price-move guard | A fresh per-leg quote whose minimum received is below the plan's minimum is 409 `PRICE_MOVED` (plan again); the web shows the fresh estimate and minimum before the wallet opens. | APPROVED 2026-10-01; ADR-014 |
| D-074 | Bitcoin PSBT limits | Quoted PSBT: segwit and Taproot inputs only (legacy input amounts are not signature-committed), deposit output equals the leg amount, OP_RETURN memo, refund output to the user (required), miner fee at most min(2% of the sale, 100,000 sats); the user-signed PSBT must spend exactly the quoted inputs. A full native Bitcoin sell keeps the fee ceiling back. | APPROVED 2026-10-01; ADR-014 |
| D-075 | Ledger amounts come from the chain | A leg is ledgered only from chain evidence (Solana balance change, ERC-20 logs, native EVM balance change at the destination block, Bitcoin outputs). A provider-reported amount is never written; missing evidence is `UNKNOWN` with a recheck. A LI.FI `PARTIAL` is recovered only from chain evidence of the delivered token (a recovery leg sized from the chain, ledgered when it settles); without evidence it is `UNKNOWN`. | APPROVED 2026-10-01; ADR-014, ADR-017 |
| D-076 | Rebalance routing hub | A rebalance sells every reduced asset to USDC on Solana, then buys every increased asset from USDC on Solana. At the first buy's quote the available basket cash fixes a scale (`buy_scale`, a rational stored once under the operation lock): each buy is `floor(planned x num / den)`, the last buy takes the remainder, minimum received scales the same way and the price-move guard (D-073) uses it. A buy never spends free USDC outside basket cash. A buy left with no cash fails `NO_FUNDS` unsent. Direct sell-to-buy pairing is a future plan. | APPROVED 2026-10-02; ADR-015 |
| D-077 | Trade thresholds | A trade is skipped when the weight gap is under 50 bps or the value gap under 5 USDC; a version may override with `minTradeBps` (10 to 1000) and `minTradeUsdc` (1 to 100). A removed asset is sold in full. No trade left means `{ aligned: true }`: the version is recorded and no operation is created. Planning uses reconciled allocated quantities, fresh prices and basket cash; stale data is 409 `DATA_STALE`, a shortfall 409 `REPAIR_REQUIRED`. | APPROVED 2026-10-02; ADR-015 |
| D-078 | Basket cash | Unspent sale proceeds are an append-only `position_cash_entries` ledger (micro-USDC, signed): sells credit what arrived, buys and fees paid from cash debit. Basket cash is spent before free USDC and is reconciled against wallet USDC on Solana (pro-rata `SHORT`, Sync only). Sell to USDC and Sell former release their percentage when the operation's first sell leg settles (once; a cancelled sale releases nothing, and a sale that fails with a recovery leg releases its cash share at the failure); leaving makes it outside-basket. | APPROVED 2026-10-02; ADR-015 |
| D-079 | Rebalance network fee placement | Extends D-071: the fee leg is first when free USDC on Solana (wallet USDC minus all baskets' cash) covers it; otherwise, when every sell is on Solana, between the sells and the buys, paid from basket cash (the leg is marked `fromCash` in both placements); otherwise 409 `INSUFFICIENT_BALANCE`. A buy-only plan short of free USDC pays from cash first. Repairs pay first from free USDC. The placement applies to the total of all fees in the fee leg (D-089); when paid from cash, the cash entry debits the total. | APPROVED 2026-10-02; amended 2026-10-02; ADR-015, ADR-016 |
| D-080 | Repair and sync | One `repair` operation per short deployment covers every affected basket: fee first, one buy of the total shortfall with free USDC (cost rounded up with slippage). On settlement the received amount is split by shortfall, remainder to the largest, each capped at its shortfall; excess stays outside baskets, a deficit stays `SHORT`. Reconciliation skips, per user, every deployment on a leg in `SUBMITTING`, `SUBMITTED`, `PENDING_CHAIN` or `UNKNOWN` (from or to), the user's basket cash and drift (no row, no notice), and Sync or Buy back on such an asset is 409 `OPERATION_IN_PROGRESS`. Sync reconciles first and compares the submitted split with the fresh figures: a different total or set of baskets is 409 `SHORTFALL_CHANGED` with the fresh total and positions, a duplicate basket or a quantity above the recorded one is 400 `VALIDATION_FAILED`; it is idempotent per key and a different body under the same key is refused. Repair needs an active route for the deployment (not basket investability) and stores the oldest affected position's applied version. Cash is never bought back. | APPROVED 2026-10-02; ADR-015 |
| D-081 | Position states, drift and keep custom | Version, backing, allocation and execution are separate derived states with one headline (execution pending, repair required, execution incomplete, rebalance available, drifted, customized, aligned); a skipped version does not raise the headline. Drift is a weight at least `driftThresholdBps` (default 500) from its target, computed with fresh prices on each reconciliation. Keep custom snapshots weights and silences prompts until a weight moves a threshold from the snapshot or the user reverts or rebalances. A drift notice repeats at most once per 7 days while drifted. | APPROVED 2026-10-02; ADR-015 |
| D-082 | Skip, continue and invalidation | A skip is one decision per position and version. Apply never replays skipped versions. A `PARTIAL` or `FAILED` rebalance shows execution incomplete with Continue (a new plan to the same target, a new network fee). Publishing a newer version cancels `PLANNED` rebalances that target an older version and that nothing was sent for (gas released); plans already targeting the new version and `IN_PROGRESS` ones are left. | APPROVED 2026-10-02; ADR-015 |
| D-083 | Notifications and web push | Every event is an inbox row (unique per user and dedupe key), then email and web push through the `notifications` queue after commit, gated by `rebalance`, `portfolioUpdates` and `managerUpdates` preferences; failures never fail the business transaction and no copy says a trade happened. Investors are told of basket pause or resume, retirement pending or retired and a lead change; a rebalance or repair ending `PARTIAL` or `FAILED` notifies once per operation (a repair notice links to the repair page). Web push is Firebase Cloud Messaging with registration tokens (`firebase-admin` `tokens`, JS SDK `getToken` with the VAPID key and `firebase-messaging-sw.js`); both APIs are deprecated in favour of Installation IDs, to be migrated later. Invalid tokens are revoked, a token registered by another user moves to the registering user, web sign-out revokes this browser's token (failures ignored), tokens are never logged, and `FIREBASE_SERVICE_ACCOUNT` is optional. Mobile push is deferred. | APPROVED 2026-10-02; ADR-015 |
| D-084 | Manager adoption counts | Per published version, over open positions holding that version or older: applied, skipped, in progress, not responded and open positions, each cell masked independently as `"<5"` for 1 to 4; no identities, wallets or amounts; basket `read` access. Joint masking is open. | APPROVED 2026-10-02; ADR-015 |
