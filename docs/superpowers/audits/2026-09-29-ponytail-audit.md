What moves where:
- `apps/api/src/db/**` and `apps/api/drizzle.config.ts` go to `packages/db`. The `db:generate`, `db:migrate` and `db:dev-roles` scripts move with it. `loadDotEnvIfPresent` disappears (item 8).

- Duplicated web/mobile logic (item 1) goes to `packages/app-core`. Platform-specific parts stay in the apps: the AppKit hooks (`use-wallet-connector`), the mobile `AppState` timeout, and all JSX.

## 4. Provider fixes

Docs were fetched on 2026-09-29 with WebFetch. Where a page was silent, that is stated rather than guessed.

- Resend, missing idempotency key on the OTP email. Docs: the `Idempotency-Key` (SDK option `idempotencyKey`) prevents duplicates, expires after 24 hours, is at most 256 characters, and the recommended pattern is `<event-type>/<entity-id>`. `ResendEmailSender.sendOtp` sends none, so a client or network retry can send a second code. Fix: pass `idempotencyKey: "contact-otp/" + verification.id` (the id is already generated in `send()`). The SDK returns `{ data, error }` inline and docs say to check `error` rather than rely on try/catch, so the outer `try/catch` is redundant (error shape is `{ name, message }`). The pages state no rate-limit or retry guidance. [apps/api/src/adapters/email-sender.ts:12-25] Docs: https://resend.com/docs/send-with-nodejs and https://resend.com/docs/api-reference/emails/send-email
- Twilio Verify create, failure mapping. Docs: create is not strictly idempotent (identical requests can create separate attempts); 429 means rate limit and the recommendation is exponential backoff with jitter; `60203` is max send attempts; `to` must be E.164 (the code sends libphonenumber `number`, correct). The code maps every start failure, including 429 and 60203, to `DeliveryError`, then `OTP_DELIVERY_FAILED` (503). Fix: map 60203 and 429 to `OTP_COOLDOWN` or `RATE_LIMITED` with a Retry-After. Do not auto-retry, because create is not idempotent. [apps/api/src/adapters/sms-otp.ts:20-27] Docs: https://www.twilio.com/docs/verify/api/verification
- Twilio Verify check, error classification. Docs: statuses are `approved`, `pending`, `canceled`, `expired`, `max_attempts_reached`, `failed`, `deleted`; `20404` means the verification expired, was already approved, or hit max attempts. The fetched page attributes `60202` to Silent Network Auth failures, not to "max check attempts" as the code comment states. Fix: keep `404/20404` as rejected and re-verify the `60202` meaning in the Twilio error dictionary before relying on it. The page gives no 429 guidance for checks, so the current handling (delivery failure, attempt given back) is reasonable. `verificationSid` is accepted in place of `to`; docs do not prefer either, so the stored `providerRef` is unused for checking. [apps/api/src/adapters/sms-otp.ts:9-14, 29-37] Docs: https://www.twilio.com/docs/verify/api/verification-check
- BullMQ job schedulers (only relevant if item 2 is not taken). `upsertJobScheduler(id, { pattern, tz }, { name, data, opts })` matches the docs and `tz: "UTC"` is the current form. Deviation: the template passes no `opts`, and the docs put `attempts`/`backoff`/`removeOnFail` in the template. Use `{ name: "purge", opts: { attempts: 3, backoff: { type: "exponential", delay: 60000 }, removeOnComplete: true, removeOnFail: 100 } }`. The page does not mention `maxRetriesPerRequest: null`; the code sets it, which BullMQ workers need (documented elsewhere). `redis-options.ts` exists because of a stale comment: BullMQ 6.3.9 declares `ioredis >=5` as a peer and resolves the same ioredis 6.0.0 here, so `connection: new Redis(url, { maxRetriesPerRequest: null })` works and the URL parser can go. [apps/api/src/worker.ts:15-23; apps/api/src/config/redis-options.ts] Docs: https://docs.bullmq.io/guide/job-schedulers
- Reown AppKit (web, Next). Docs: `WagmiAdapter` with cookie storage (`createStorage({ storage: cookieStorage })`) and `ssr: true`, then `cookieToInitialState(wagmiAdapter.wagmiConfig, headers.get("cookie"))` in `app/layout.tsx`, passed as `initialState` to `WagmiProvider`, with `QueryClientProvider` around it; metadata `url` must match the real domain. The code sets `ssr: true` but has no cookie storage, no `cookieToInitialState` and no `initialState`, so wagmi state is not hydrated from the server. Fix: add cookie storage, read the cookie header in the server layout, and thread `initialState` through `Providers` into `WagmiProvider`. Also `NEXT_PUBLIC_APP_URL` falls back to localhost in metadata; require it in production. [apps/web/lib/appkit.tsx:16, 35-37; apps/web/components/providers.tsx:28-35] Docs: https://docs.reown.com/appkit/next/core/installation
- Reown AppKit (React Native). Docs: `@walletconnect/react-native-compat` must be the very first import; `storage` is a required `createAppKit` option implementing `getItem/setItem/removeItem/getKeys/getEntries`; `metadata.redirect.native` is set; Android `<queries>` lists wallet packages. The code follows all four (`polyfills.ts` starts with compat, custom `appKitStorage`, redirect `bytesac://`, `wallet-queries.js` plugin). Only verify that `polyfills.ts` is imported before anything else in the entry, and drop the `text-encoding` line (item 19). No API deviation found. Docs: https://docs.reown.com/appkit/react-native/core/installation
- Drizzle migrations. Generate then apply with runtime `migrate()` is a documented path; `drizzle-kit migrate` is the CLI alternative reading the same journal. No deviation. Optional: `db:migrate` can be `drizzle-kit migrate` (the config already reads `MIGRATOR_DATABASE_URL`), which removes the `argv[1] === import.meta.url` entry guard in `migrate.ts`. Keep `runMigrations` for the tests. `schemaFilter: ["app"]` is documented. Docs: https://orm.drizzle.team/docs/migrations
