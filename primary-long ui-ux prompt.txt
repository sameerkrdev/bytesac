# 3. UNDERSTAND BYTESAC BEFORE DESIGNING
============================================================

Bytesac is a strategy-driven investment platform designed to make
investing across on-chain assets simpler, more understandable and more
user-controlled.

The product connects:

Investors
+
Investment Baskets
+
Verified Managers
+
Organizations
+
Multi-chain Assets
+
Portfolio
+
Execution
+
Rebalancing.

The central product idea is:

> INVEST IN STRATEGIES, NOT INDIVIDUAL TRADES.

Instead of forcing users to manually research and construct portfolios
asset-by-asset, Bytesac allows users to discover investment baskets,
understand the strategy behind them, invest into them, monitor their
portfolio and review future strategy changes.

The platform currently focuses on approved:

- crypto assets
- crypto tokens
- supported RWAs

across supported networks.

The Asset Registry is the source for approved assets and their supported
deployments/routes.

# 6. SECONDARY AUDIENCE — STRATEGY / FUND MANAGERS
============================================================

Managers are professionals or experienced investors who create and
maintain investment strategies.

Managers need to:

- operate through an organization
- create baskets
- define investment objectives
- define investment thesis
- select approved assets
- define target allocations
- define risk information
- configure rebalance behavior
- define fees
- submit baskets for platform review
- publish strategies
- create new basket versions
- communicate strategy updates
- monitor strategy performance
- manage their organization/team.

Important:

A basket belongs to the verified organization.

It is NOT:

- the personal wallet of a manager
- the personal asset of an individual manager
- the investor's portfolio.

The relationship is conceptually:

USER
 ↓

 ↓
ORGANIZATION
 ↓
BASKET

 ↓

Manager UX should feel:

# 7. ORGANIZATION MODEL
============================================================

Bytesac separates:

USER
ORGANIZATION
BASKET
MANAGER ASSIGNMENT
INVESTOR PORTFOLIO.

A user can belong to an organization with different roles.

Possible roles include:

- Owner
- Admin
- Manager
- Analyst
- Viewer.

Permissions are role-based and may also be basket-specific.

The organization is the durable owner of the basket.

If an individual manager leaves the organization, the basket does not
become their personal property.

Manager history and assignments should remain auditable.

The UI should reflect this distinction.

Do NOT design the product as:

Individual Manager
    ↓
Personal Basket.

Organization
    ↓

    ↓
Assigned Managers / Team.

============================================================
# 8. WHAT IS A BASKET?
============================================================

A Basket is a versioned investment strategy owned by a verified
organization.

A basket defines things such as:

- name
- description
- investment objective
- investment thesis
- strategy
- intended investor profile
- assets
- target allocations
- constraints
- risk information
- rebalance methodology
- rebalance frequency/thresholds
- manager information
- fees
- minimum investment
- disclosures.

A basket is NOT simply a list of tokens.

It should feel like:

> A complete investment strategy that an investor can research and
> understand.

Therefore the Basket UX should be a major product experience.

# 10. BASKET LIFECYCLE
============================================================

A basket begins as:

DRAFT
    ↓
SUBMITTED
    ↓
PLATFORM REVIEW
    ↓
APPROVED
    ↓
PUBLISHED
    ↓
VERSIONED UPDATES
    ↓
PAUSED / RETIRED / ARCHIVED.

A draft is NOT publicly investable.

A published basket version is immutable.

When a manager changes the strategy, the system creates a new version
rather than silently changing historical strategy information.

Example:

Basket v1
    ↓
Basket v2
    ↓
Basket v3
    ↓
Current.

The UI should make version history understandable and trustworthy.

============================================================
# 11. MANAGER STRATEGY VS INVESTOR PORTFOLIO
============================================================

This distinction is extremely important.

There are three different concepts:

### 1. Manager Strategy

What the basket SHOULD target.

Example:

BTC 35%
ETH 30%
SOL 20%
RWA 15%.

### 2. User Basket Allocation

How the platform logically attributes the user's investment to that
basket.

### 3. Verified Holdings

What the user actually owns/controls based on the relevant chain,
wallet or issuer/provider state.

These MUST NOT be visually or conceptually conflated.

The UI should never imply:

"Manager says 35% BTC, therefore the user's wallet definitely has 35%
BTC."

Actual holdings must be represented separately.

# 13. USER ASSET OWNERSHIP / NON-CUSTODIAL PHILOSOPHY
============================================================

This is one of Bytesac's most important product principles.

Bytesac is designed around USER CONTROL of the underlying investment
assets rather than the traditional model where a centralized platform
takes custody of user assets.

The intended conceptual model is:

USER
 ↓
USER WALLET / USER-CONTROLLED ASSET
 ↓
USER AUTHORIZATION
 ↓
SUPPORTED ON-CHAIN EXECUTION.

NOT:

USER
 ↓
DEPOSIT ASSETS INTO BYTESAC
 ↓
BYTESAC HOLDS USER ASSETS
 ↓
BYTESAC CONTROLS USER ASSETS.

The product should communicate:

> YOUR ASSETS.
> YOUR WALLET.
> YOUR AUTHORIZATION.
> YOUR DECISION.

The user should understand that Bytesac is helping them discover,
research, construct and manage an investment strategy without relying
on a traditional centralized custody model.

This should be a major differentiation from custodial investment
platforms.

However:

DO NOT invent technical, legal or security guarantees that are not
supported by the architecture.

Do not claim:

- "Your assets can never be stolen."
- "Impossible to hack."
- "100% guaranteed non-custodial."
- "Bytesac can never interact with your assets."

Instead communicate the supported product principle:

- user-controlled assets
- user-authorized execution
- wallet ownership/control
- transparent on-chain ownership
- explicit transaction authorization
- no traditional custodial deposit experience.

The exact custody/account model remains chain/asset dependent and must
follow the documented architecture.

# 18. REBALANCING
============================================================

Rebalancing is NOT automatic control by the manager.

A manager defines the strategy.

A new basket version represents a new target.

The user's portfolio is NOT silently changed when the manager publishes
the new version.

The flow is:

MANAGER
creates new version
    ↓
PLATFORM REVIEW
    ↓
VERSION PUBLISHED
    ↓
USER NOTIFIED
    ↓
USER REVIEWS CHANGES
    ↓
USER CHOOSES:
    PARTICIPATE
    OR
    SKIP
    ↓
IF PARTICIPATE:
USER AUTHORIZES EXECUTION
    ↓
ON-CHAIN EXECUTION
    ↓
RECONCILIATION.

This distinction is fundamental to Bytesac.

============================================================
# 20. SKIPPING A REBALANCE
============================================================

If a user skips a manager update:

NO TRADE OCCURS.

The user's current holdings remain unchanged.

The user remains associated with the previous applied basket version.

If a later version is accepted, the platform should calculate from the
CURRENT VERIFIED HOLDINGS to the selected target.

Do not visually imply that the system replays every skipped version.

============================================================
# 21. DRIFT AND EXTERNAL WALLET ACTIVITY
============================================================

Users can manually buy, sell or transfer assets outside a Bytesac
strategy flow.

This can create:

- weight drift
- allocation mismatch
- missing quantity
- unassigned assets
- incomplete execution
- stale data.

The UI should explain WHAT happened rather than simply showing:

"ERROR."

Example:

> Your wallet activity changed the assets associated with this basket.

Then explain:

- what changed
- when it changed
- affected asset
- current holding
- target holding
- available actions.

Possible actions:

RESTORE
    or
KEEP CUSTOM ALLOCATION
    or
REBALANCE
    or
REVIEW.

Never silently buy an asset simply because a manager strategy expects
it.

============================================================

Possible states:

- Weight Drift
- Allocation Shortfall
- Unapplied Version
- Execution Incomplete
- Data Stale
- RWA Settlement Pending
- Customized.

The user should understand the cause before seeing the action.

Example:

CURRENT
BTC 35%
ETH 45%
SOL 20%

TARGET
BTC 40%
ETH 35%
SOL 25%

Then:

Do not make repair flows feel like error screens.

============================================================
# 24. CORE PRODUCT PROBLEMS WE ARE SOLVING
============================================================

Design should solve these problems:

### Problem 1 — Discovery

There are too many assets and strategies.

Bytesac provides curated baskets and discovery.

### Problem 2 — Research

Users struggle to understand what they are buying.

Bytesac provides deep basket and manager research.

### Problem 3 — Complexity

Multi-chain investing is technically complicated.

Bytesac abstracts unnecessary blockchain complexity.

### Problem 4 — Portfolio construction

Users manually build portfolios and rebalance them.

Bytesac provides strategy-driven baskets.

### Problem 5 — Execution complexity

Multiple assets may require multiple transactions/routes.

Bytesac provides a guided investment/execution experience.

### Problem 6 — Lack of control

Traditional custodial platforms can place users' assets under platform
control.

Bytesac is designed around user-controlled assets and explicit
authorization.

### Problem 7 — Strategy changes

Manager strategy changes can be confusing.

Bytesac shows version differences and lets the user decide whether to
participate.
